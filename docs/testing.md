# Инфраструктура тестирования ядра

## Уровни проверки

Каждый инкремент ядра проходит четыре последовательных уровня:

1. `cargo fmt --all -- --check` фиксирует единое форматирование;
2. модульные проверки `no_std`-библиотек выполняются на хосте;
3. release-сборка создаёт загрузочный UEFI-образ;
4. QEMU с OVMF загружает настоящий образ и проверяет обязательные признаки в последовательном журнале.

Успех только модульных тестов недостаточен для кода, зависящего от таблиц страниц, уровней привилегий, системных вызовов, APIC или переключения контекста.

## Модульные проверки

CI явно перечисляет все библиотеки ядра, чтобы новый пакет не был принят вместо случайно пропущенного существующего:

```bash
cargo test -p phoenix-framebuffer
cargo test -p phoenix-memory
cargo test -p phoenix-vm
cargo test -p phoenix-scheduler
cargo test -p phoenix-process
cargo test -p phoenix-syscall-abi
cargo test -p phoenix-capability
cargo test -p phoenix-ipc
```

Новый библиотечный пакет обязан быть добавлен в этот список в том же PR.

## Проверочная загрузка QEMU

`scripts/run-qemu-ci.sh` принимает путь к UEFI-образу, находит OVMF, запускает QEMU без графического окна и сохраняет последовательный вывод. Ядро завершает успешную проверку через `isa-debug-exit`; ожидаемый код процесса QEMU — 33.

Пример локального запуска после сборки:

```bash
mkdir -p artifacts
IMAGE="$(cargo run --release --quiet)"
bash scripts/run-qemu-ci.sh "$IMAGE"
```

Переменные `OVMF_CODE` и `OVMF_VARS` позволяют явно указать файлы прошивки, если они находятся вне стандартных путей.

## Реестр обязательных маркеров

`tests/qemu/bootstrap.markers` — единственный реестр строк, без которых загрузка считается неуспешной. Пустые строки и строки с `#` игнорируются.

Новая аппаратная или сквозная самопроверка обязана:

- завершаться однозначной строкой вида `<subsystem> self-test: OK`;
- добавить эту строку в реестр в том же PR;
- завершить ядро ошибкой до `bootstrap: OK`, если проверка не прошла.

`scripts/check-serial-markers.sh` проверяет реестр без зависимости от порядка диагностических строк. Его собственный положительный и отрицательный сценарии запускаются через `scripts/test-check-serial-markers.sh`.

Другой набор признаков можно выбрать переменной `PHOENIXOS_MARKERS_FILE`. Это позволяет позднее добавить отдельные сценарии загрузки, не копируя QEMU-раннер.

## Требования к изменениям

Пункт дорожной карты считается подтверждённым только когда соответствующие тесты, обязательный QEMU-маркер и документация находятся в одной ветке и полный CI зелёный. Нестабильные задержки и ожидание по времени не должны использоваться вместо наблюдаемого аппаратного события или явного маркера.
