# Процессы и адресные пространства

Этап 0.1 вводит модель процессов отдельно от конкретного формата таблиц страниц. Это позволяет сначала зафиксировать правила владения, состояния и виртуальные области, а затем подключить реальные адресные пространства x86-64 без смешивания ответственности.

## Идентификаторы и жизненный цикл

Библиотека `phoenix-process` работает без стандартной библиотеки и без обязательной динамической памяти.

Каждый процесс получает:

- отдельный идентификатор процесса;
- отдельный идентификатор адресного пространства;
- явное состояние жизненного цикла.

Поддерживаемые состояния:

- создан;
- готов к выполнению;
- заблокирован;
- завершён.

Переходы проверяются. Например, созданный процесс нельзя сразу перевести в заблокированное состояние, а незавершённый процесс нельзя удалить из таблицы процессов. Завершение выполняется отдельной операцией `exit`: только готовый или заблокированный процесс переходит в `Exited`, и его запись сохраняет полный 64-битный статус до удаления.

## Виртуальные области

Адресное пространство хранит набор описателей виртуальных областей фиксированной вместимости.

Для каждой области задаются:

- начальный виртуальный адрес;
- длина;
- права чтения, записи и выполнения;
- доступность из пользовательского режима;
- назначение области: программа, куча, стек, общая память, отображённая память или зарезервированная область ядра.

При добавлении проверяются:

- ненулевая длина;
- выравнивание начала и длины по 4 КиБ;
- переполнение адреса;
- каноничность первого и последнего адреса x86-64;
- отсутствие пересечений с уже зарегистрированными областями;
- наличие свободной служебной записи.

## Разрез адресного пространства

Текущий bootloader размещает ядро и его служебные отображения не только в верхней канонической половине. В QEMU код ядра находится примерно в P4[2], стек — в P4[3], а линейное отображение физической памяти начинается в P4[2].

Поэтому на этапе 0.1 отдельный процесс получает собственный P4[0], то есть виртуальный диапазон 0–512 ГиБ. Записи P4[1..511] наследуются из системного адресного пространства и считаются разделяемыми системными отображениями. Их дочерние таблицы принадлежат ядру и не освобождаются вместе с процессом. Это решение зафиксировано в D-010.

## Проверки

Модульные проверки подтверждают:

- запрет пересекающихся виртуальных областей;
- поиск области по адресу и точное удаление;
- отказ для невыровненных и неканонических диапазонов;
- допустимые переходы жизненного цикла процесса;
- сохранение 64-битного статуса завершения;
- отказ для недопустимых переходов;
- ограничение вместимости таблицы процессов.

Автоматическая проверка запускает `cargo test -p phoenix-process`.

## Реальный корень таблиц страниц

Следующий инкремент добавляет `InactivePageTable` в подсистему виртуальной памяти. Объект выделяет отдельную физическую страницу для P4 через системный распределитель, получает к ней доступ через внутреннее линейное отображение физической памяти и полностью обнуляет таблицу.

Новый корень остаётся неактивным до явной проверки переключения CR3. Он наследует только постоянные отображения верхней половины ядра, а пользовательская нижняя половина создаётся отдельно и принадлежит процессу.

QEMU-проверка подтверждает, что:

- корень получает отдельную физическую страницу;
- новый корень не совпадает с активным CR3;
- пользовательская половина новой P4 пуста, а верхняя половина содержит только унаследованные ядерные записи;
- создание занимает ровно одну физическую страницу;
- освобождение пустого корня полностью возвращает страницу системному распределителю.

Успешный путь выводит маркер `process page table root self-test: OK`.

## Разделяемые системные P4-отображения

Новый корень процесса копирует из активной P4 записи с индексами 1–511. P4[0] остаётся отдельным пользовательским окном. Копируются только записи верхнего уровня: дочерние таблицы системных отображений остаются общими и принадлежат системному адресному пространству.

Перед уничтожением корня процесса разделяемые P4[1..511] очищаются без освобождения дочерних таблиц. P4[0] остаётся отдельным и предназначен для пользовательских отображений.

## Пользовательские отображения и владение

Неактивное адресное пространство умеет выделять собственную физическую страницу, обнулять её и отображать в нижней канонической половине с `USER_ACCESSIBLE`. При создании такого отображения промежуточные P3/P2/P1 также выделяются из системного распределителя.

Все листовые страницы, созданные этим API, считаются принадлежащими процессу. При уничтожении пользовательской половины они освобождаются вместе с собственными таблицами P1/P2/P3. Общая верхняя половина ядра при этом не обходится и не освобождается.

QEMU-проверка создаёт пользовательское отображение, проверяет его трансляцию, записывает контрольное значение через физическое отображение памяти, затем рекурсивно уничтожает пользовательскую половину и подтверждает возврат памяти. Успешный путь выводит маркер `process user mapping self-test: OK`.

## Связь VirtualRegion с таблицами страниц

Ядерный адаптер `ProcessAddressSpace` объединяет чистую модель `AddressSpace` и реальный `InactivePageTable`. При добавлении пользовательского региона он переводит права `VirtualRegion` в флаги x86-64, создаёт все 4-КиБ отображения диапазона и регистрирует регион в модели. Если создание одной из страниц не удаётся, уже созданные страницы откатываются, а запись региона удаляется.

При снятии региона его листовые кадры возвращаются системному распределителю; промежуточные таблицы окончательно освобождаются при уничтожении адресного пространства. QEMU-проверка создаёт двухстраничный регион, подтверждает трансляцию обеих страниц, снимает его и проверяет отсутствие утечки памяти. Успешный путь выводит маркер `process region mapping self-test: OK`.

## Загрузка байтов пользовательской программы

Адресное пространство процесса умеет записывать байты в уже отображённые пользовательские страницы через линейное отображение физической памяти ядра. Для этого не требуется временно переключать CR3 процесса и не требуется делать исполняемую страницу записываемой для пользовательского кода.

Запись проверяет границу раннего пользовательского окна и наличие каждой затрагиваемой страницы. Копирование выполняется по страницам, поэтому корректно работает и для диапазона, пересекающего границу двух физических кадров.

QEMU-проверка записывает короткую последовательность машинных байтов через границу двух пользовательских страниц и считывает её обратно через физическое отображение. Успех подтверждается маркером `process user image write self-test: OK`.

Этот путь предназначен как общая основа для первого пользовательского теста и будущего загрузчика ELF.

## Переключение CR3

`InactivePageTable::activate` временно записывает корень процесса в CR3 и возвращает guard, который при уничтожении восстанавливает прежний корень и его флаги. Вызывающая сторона обязана гарантировать, что исполняемый код, текущий стек и необходимые данные доступны через унаследованные системные P4-отображения.

QEMU-проверка дополнительно проверяет, что код, стек и physical-memory map находятся за пределами пользовательского P4[0], отключает прерывания, активирует корень процесса, записывает и читает контрольное значение через пользовательский виртуальный адрес и затем уничтожает guard. После возврата в системный CR3 контрольное значение проверяется через физическое отображение, регион снимается, а все выделенные страницы возвращаются распределителю.

Успешный путь выводит маркер `process cr3 switch self-test: OK`. После зелёной обязательной проверки пункт «модель процессов и адресных пространств» этапа 0.1 считается завершённым.

## Дальше

Модель уже связана со штатным `process_exit`: QEMU запускает код в CPL3, получает статус через системный вызов и переводит соответствующую запись таблицы в `Exited`. Следующий инкремент должен снять завершённый пользовательский процесс с планировщика, сохранив статус до безопасной очистки ресурсов.
