# Пользовательская среда выполнения

Первый слой пользовательской среды выполнения вынесен в отдельный `no_std`-модуль `phoenix-user-runtime`. Он зависит только от стабильного `phoenix-syscall-abi` и не импортирует внутренние типы ядра.

## Системные вызовы x86-64

Низкоуровневый переход использует регистровый контракт PhoenixOS:

- RAX — номер системного вызова и возвращаемое значение;
- RDI, RSI, RDX, R10, R8, R9 — шесть аргументов;
- RDX после возврата содержит отдельный статус;
- RCX и R11 считаются разрушенными инструкцией `SYSCALL`.

Статус `0` преобразуется в успешный результат, ненулевой статус возвращается вызывающему коду без потери 64-битного пространства значения.

## IPC

Среда выполнения уже предоставляет обёртки `ipc_send` и `ipc_receive`. Они принимают типизированный capability handle, обычные Rust-срезы слов и C-совместимые метаданные получения. Адреса и размеры переводятся в стабильный ABI непосредственно перед системным вызовом.

Передаваемая capability задаётся явно через `Option<PackedCapabilityHandle>`. При отсутствии передачи в ABI помещается `NO_TRANSFERRED_CAPABILITY`.

## Вход и завершение процесса

`start` сохраняет совместимость с функцией `main` без аргументов. Новый `start_with_info` принимает C-совместимую функцию и передаёт ей указатель на проверенный блок `ProcessStartInfo`, который ядро помещает в `RDI` перед входом в x86-64 программу. Оба варианта передают возвращённый 64-битный статус в публичный системный вызов `process_exit`. Если ядро ошибочно вернёт управление после запроса завершения, runtime выполняет `UD2`, чтобы пользовательская программа не продолжила работу в неопределённом состоянии.

`ProcessStartInfo` имеет стабильную C-компоновку размером 40 байт: версия и флаги по 32 бита, затем 64-битные число аргументов, адрес массива аргументов, число записей окружения и адрес массива окружения. Каждый элемент массивов — `ProcessStartString { address, length }`; строки являются байтовыми диапазонами и не требуют завершающего нуля. ABI версии 0 допускает не более 256 записей каждого вида и оставляет флаги нулевыми.

Ядро принимает любой 64-битный статус, возвращает управление из CPL3 в точку запуска и отдаёт статус вызывающему слою процесса. Тот же путь используется проверочным ELF-образом; отдельного служебного syscall завершения больше нет.

## Граница текущего шага

Минимальный жизненный цикл `start → main → process_exit` завершён: полученный статус сохраняется в таблице, процесс снимается с планировщика, а запись очищается только после освобождения ресурсов. Аргументы и окружение запуска теперь передаются через версионированный C-совместимый блок. TLS, конструкторы, стандартная библиотека и первый системный сервис остаются следующими слоями runtime и управления процессами.
