# Измерения процессоров до передачи управления ядру

Редакция: 12 ноября 2026 года. Программная подзадача №342.

## Назначение

Отдельная утилита `tools/uefi-ap-probe` выполняется внутри QEMU
**до завершения работы загрузочных служб UEFI**. Она использует
официальный протокол MP Services для выполнения одного короткого
обработчика на каждом включённом вспомогательном процессоре.

Подход позволяет получить **настоящие измерения, сделанные самими
процессорами** без самостоятельной реализации старта в 16-битном режиме,
изменения таблиц страниц и управления локальным APIC. Прошивка отвечает
за запуск, выделение стеков и возврат вспомогательных процессоров.

Это **не механизм запуска остальных ядер работающей PhoenixOS**:
после передачи управления ядру UEFI MP Services недоступна.
Зафиксированная здесь CR3 принадлежит этапу прошивки и не доказывает
учёт CR3 ядра или загрузчика после завершения его работы.

## Что измеряется

- Реальный идентификатор APIC каждого исполняющегося процессора.
- Действующее значение CR3 в фазе UEFI.
- PAT, MTRRCAP, MTRRdefType.
- Все заявленные переменные MTRR в пределах строгой вместимости,
  фиксированные MTRR при их включении и поддержке.
- Принадлежность полученных идентификаторов списку включённых ЦП,
  полученному из UEFI, отсутствие повторов.
- Совпадение режимов кэширования между измеренными процессорами.

При неподдерживаемых регистрах, переполнении 64 процессоров,
разночтениях, неполном запуске или повторном APIC ID результат
считается **неуспешным**. Для AMD SYSCFG и TOP_MEM2 в QEMU намеренно
не выполняется чтение: виртуальная модель может не поддерживать эти MSR.
Поэтому диагностика не выдаёт подтверждение всей реальной конфигурации AMD.

## Безопасность

Программа принимает к исполнению только гостевую систему QEMU/KVM
или QEMU/TCG по идентификатору гипервизора. Это дополнительная проверка,
а не криптографическое доказательство происхождения окружения.
**На физическом ASUS запускать эту утилиту нельзя.**

Не подключаются рабочие драйверы PhoenixOS и устройства для передачи DMA,
не читается и не изменяется конфигурация PCI, не меняются PAT/MTRR,
не производится запись в MSR, не создаются отображения памяти,
не открываются диски. Вывод выполняется в виртуальный последовательный
порт QEMU. Загрузочный образ монтируется только для чтения,
а единственные изменяемые сведения UEFI хранятся в временном файле
виртуальной машины.

Протокол всегда сообщает
`kernel_cr3_verified=false dma_authorized=false`. Успех UEFI
не повышает аппаратный счётчик 16/17 или 17/17 и не разрешает
активные испытания DMA на ноутбуке.

## Сборка и проверка

Зависимости закреплены отдельно от рабочего ядра в
`tools/uefi-ap-probe/Cargo.lock`. Для сборки нужен компилятор
`nightly-2026-11-10` с целью `x86_64-unknown-uefi`.

```sh
rustup target add x86_64-unknown-uefi
cargo build --manifest-path tools/uefi-ap-probe/Cargo.toml --target x86_64-unknown-uefi --release --locked
python3 tests/platform/test-uefi-ap-probe.py
sudo python3 scripts/run-uefi-ap-probe.py \
  tools/uefi-ap-probe/target/x86_64-unknown-uefi/release/phoenix-uefi-ap-probe.efi \
  artifacts/uefi-ap-probe-serial.log
```

Для самостоятельной проверки виртуального профиля из 12 процессоров
используется окружение `PHOENIX_AP_PROBE_CPUS=12` для последней команды.
Выполнение функции на вспомогательных ядрах происходит в службах
прошивки. Внутренний ограничитель UEFI намеренно не прерывает их на
середине измерения: весь процесс QEMU ограничен внешним сроком 120 секунд,
что предотвращает возврат приложения при ещё работающих обработчиках.

Последняя команда допускается только на испытательной системе Linux
с QEMU/KVM, OVMF, `mkfs.vfat`, `mtools` и отдельным виртуальным
носителем. Общая автоматическая проверка повторяет этот сценарий
в двух режимах: с четырьмя и двенадцатью процессорами. Успех
объявляется только после получения соответственно 4/4 либо 12/12
отдельных действительных снимков.

## Что требуется для 16/17

- Запуск вспомогательных процессоров **после загрузки ядра**, а не
  во временной среде UEFI.
- Проверка всех действующих корней CR3, включая созданные загрузчиком,
  другие и меняющиеся адресные пространства.
- Полные снимки PAT/MTRR и AMD SYSCFG/TOP_MEM2 со всех логических ЦП
  на ASUS; сравнение с отображениями памяти и их псевдонимами.
- Повторная согласованная проверка при изменении таблиц страниц.

Только после полной пассивной аппаратной проверки возможно закрытие
16/17. Для 17/17 отдельно необходимы действующий AMD IOMMU,
подтверждённая изоляция устройства и безопасный физический контроллер.
