# Начальное межпроцессное взаимодействие

## Назначение

Первый слой IPC PhoenixOS предоставляет небольшой предсказуемый транспорт сообщений между процессами без динамических выделений памяти внутри очереди.

Очередь остаётся внутренней моделью ядра, а пользовательская граница теперь закреплена отдельным контрактом ABI. Задача текущего слоя — сохранить предсказуемые свойства транспорта до подключения проверки пользовательской памяти, блокировок потоков и реального диспетчера IPC.

## Конечная точка

Конечная точка имеет идентификатор и ограниченную очередь сообщений фиксированной вместимости.

Операция отправки:

- не выделяет память;
- сохраняет порядок FIFO;
- возвращает явную ошибку, если очередь заполнена.

Операция получения:

- возвращает самое старое сообщение;
- возвращает явную ошибку, если очередь пуста.

На первом этапе операции неблокирующие. Блокировка отправителя или получателя будет связана с планировщиком отдельным инкрементом.

## Сообщение

Начальное сообщение содержит:

- идентификатор процесса-отправителя;
- до шести 64-битных слов полезной нагрузки;
- при необходимости новый дескриптор переданной возможности получателя.

Небольшая встроенная полезная нагрузка позволяет передавать управляющие сообщения без кучи и хорошо сочетается с текущим шестирегистровым ABI системных вызовов.

Большие данные в дальнейшем должны передаваться через разделяемую память или другие объекты памяти, доступ к которым выдаётся возможностями.

## Передача возможностей

Операция отправки с возможностью выполняется как единое логическое действие:

1. проверяется размер сообщения;
2. проверяется свободное место в очереди;
3. проверяется возможность переноса в таблицу получателя;
4. возможность атомарно перемещается между таблицами процессов;
5. новый дескриптор получателя помещается в сообщение;
6. сообщение добавляется в очередь.

Если очередь заполнена или таблица возможностей получателя не имеет свободного места, исходный дескриптор остаётся действительным у отправителя, а сообщение не появляется в очереди.

На текущем однопоточном уровне модели промежуточное состояние не наблюдаемо. При подключении к параллельному ядру эта же операция должна быть защищена общей синхронизацией конечной точки и таблиц возможностей.

## Контракт системных вызовов

Для неблокирующих операций зарезервированы номера `0x100` (`ipc_send`) и `0x101` (`ipc_receive`). Оба вызова используют общий шестирегистровый ABI PhoenixOS.

Дескриптор возможности упаковывается в одно 64-битное слово: младшие 32 бита содержат номер слота, старшие 32 бита — поколение. Отсутствующая передаваемая возможность кодируется значением `u64::MAX`.

`ipc_send` передаёт дескриптор конечной точки, адрес массива слов, количество слов, необязательную возможность, флаги и нулевое зарезервированное слово. `ipc_receive` передаёт дескриптор конечной точки, адрес выходного массива, его вместимость, адрес метаданных, флаги и нулевое зарезервированное слово. Метаданные имеют стабильную C-совместимую форму из трёх 64-битных слов: идентификатор процесса-отправителя, фактическое количество слов и упакованный дескриптор переданной возможности либо `u64::MAX`.

Публичные конструкторы `SyscallRequest::ipc_send` и `SyscallRequest::ipc_receive` формируют регистровое представление одинаково для ядра, libc и будущих SDK.

## Проверки

Модульные проверки подтверждают:

- порядок FIFO;
- сохранение идентификатора отправителя;
- отказ при заполненной очереди;
- отказ при слишком большой встроенной нагрузке;
- корректный переход через конец кольцевой очереди;
- корректное поведение очереди нулевой вместимости;
- успешную передачу возможности вместе с сообщением;
- сохранение исходной возможности при заполненной очереди;
- сохранение исходной возможности и отсутствие сообщения при заполненной таблице получателя;
- реальную линковку модели с ядром и FIFO-проход двух сообщений во время загрузки QEMU с обязательным маркером `ipc endpoint self-test: OK`.

## Проверка пользовательских буферов

Общая VM-библиотека предоставляет `UserBuffer::for_array`. До обращения к пользовательской памяти ядро обязано проверить ненулевой адрес для непустого диапазона, степенное выравнивание, умножение количества элементов на их размер без переполнения и принадлежность всего полуинтервала раннему пользовательскому окну P4[0].

Пустой массив нормализуется в диапазон нулевой длины и не требует разыменования указателя. Успешная проверка диапазона ещё не означает, что все его страницы отображены с нужными правами: проверка отображений и фактическое копирование выполняются следующим отдельным слоем.

## Диспетчер системных вызовов

Номера `ipc_send` и `ipc_receive` теперь распознаются общим диспетчером системных вызовов. Перед обращением к backend диспетчер проверяет нулевое зарезервированное слово, пока не поддерживаемые флаги, максимальный размер inline-сообщения и форму пользовательских word-буферов через `UserBuffer`. Для `ipc_receive` также проверяется базовая форма адреса метаданных.

Диспетчер связывается с адресным пространством текущего процесса через короткоживущий контекст системного вызова. `ipc_send` выполняет checked copy-in, разрешает endpoint-возможность и помещает сообщение в найденную очередь. `ipc_receive` сначала проверяет payload и метаданные в пользовательской памяти, копирует результат и только после успешного copy-out удаляет сообщение из очереди. Пустая или заполненная очередь возвращает неблокирующий статус «операция ещё не готова».

Ранняя реализация допускает только один активный процессный контекст и устанавливает его при запрещённых прерываниях на время пользовательского `SYSCALL`. Это ограничение соответствует текущему однопроцессорному стеку системных вызовов; перед SMP контекст станет per-CPU. QEMU проверяет, что отображённый send-буфер принимается, неотображённый диапазон отклоняется, а receive-слова действительно записываются в адресное пространство текущего процесса. Обязательный маркер — `ipc syscall memory context self-test: OK`.

Тот же контекст содержит таблицу возможностей вызывающего процесса. Упакованный ABI-дескриптор преобразуется в слот и поколение, после чего отправка требует endpoint-возможность с правом `WRITE`, а получение — с правом `READ`. Возможность другого типа, устаревшее поколение или недостаточные права отклоняются до обращения к очереди. Успешное разрешение возвращает `EndpointId`, совпадающий с `ObjectId` возможности; QEMU требует маркер `ipc capability endpoint self-test: OK`.

Объекты endpoint хранятся в фиксированном реестре без динамического выделения памяти. Ранний syscall backend ограничен 8 endpoint-объектами с очередью по 4 сообщения; увеличение вместимости будет связано с будущим системным аллокатором объектов, а не с ростом inline-массива на стеке. Реестр обеспечивает уникальность `EndpointId`, явные ошибки переполнения и отсутствующего объекта и возвращает одну и ту же изменяемую очередь при повторном поиске. Модульные проверки и QEMU-маркер `ipc endpoint registry self-test: OK` подтверждают сохранение состояния очереди через lookup. Сквозной QEMU-тест отправляет и получает сообщение через настоящий syscall dispatcher, проверяет payload, отправителя, длину, отсутствие переданной возможности и пустую очередь; обязательный маркер — `ipc endpoint syscall operations self-test: OK`.

## Следующий шаг

Появился проверяемый примитив copy-in: неактивное пользовательское адресное пространство читает данные только через реально существующие отображения, разбивая операцию на границах 4-КиБ страниц. QEMU проверяет чтение массива, пересекающего две страницы, маркером `process user copy-in self-test: OK`.

Добавлен общий слой `ipc_user_memory`: он принимает типизированные ABI-аргументы `ipc_send`/`ipc_receive`, повторно проверяет диапазон через `UserBuffer`, предварительно убеждается, что каждое фактически используемое 64-битное слово отображено, затем выполняет checked copy-in/copy-out через `ProcessAddressSpace`. QEMU проверяет два слова через границу 4-КиБ страницы и требует маркер `ipc user word copy self-test: OK`.

`ipc_send`/`ipc_receive` теперь проходят полный путь от пользовательского буфера до очереди и обратно, включая перенос возможности. Endpoint может хранить идентификатор процесса-получателя; системный вызов находит таблицу возможностей владельца через фиксированный ранний реестр процессов. При передаче capability исходный handle сначала атомарно переносится в таблицу получателя, новый handle записывается в сообщение, и только затем сообщение становится видимым в очереди. Если очередь или таблица получателя заполнены, исходный handle остаётся действительным у отправителя. Получение из привязанного endpoint разрешено только его владельцу. Сквозной QEMU-тест проверяет исчезновение исходного handle, появление эквивалентной возможности у получателя и наличие нового handle в сообщении; обязательный маркер — `ipc capability transfer self-test: OK`. Блокирующие варианты будут интегрированы с планировщиком потоков позже.
