# Перенос приложений и игр в PhoenixOS

## Цель

PhoenixOS должна позволять использовать не только программы, написанные специально для неё. Стратегия переноса разделяется на нативную пересборку, перенос через совместимые библиотеки и запуск готовых Windows-бинарников через отдельную среду совместимости.

Приоритет всегда отдаётся нативной сборке, когда она практически возможна: она проще в сопровождении, лучше интегрируется с интерфейсом PhoenixOS и не требует дополнительного слоя выполнения.

## Быстрый выбор пути

### Есть исходный код

Сначала проверяется возможность нативной пересборки.

Наиболее удобны проекты, которые уже используют:

- C или C++;
- Rust;
- Zig;
- CMake, Meson или Cargo;
- POSIX;
- SDL;
- переносимые библиотеки работы со звуком, сетью и файлами;
- Vulkan или другой графический интерфейс, для которого есть переносимый слой.

Чем меньше программа зависит от внутренних интерфейсов конкретной ОС, тем меньше объём изменений.

### Исходного кода нет

Если доступен только Windows-бинарник PE, применяется среда совместимости Win32/Win64.

Первое исследовательское направление:

```text
Windows-программа или игра
        |
     Wine
        |
Windows API -> службы PhoenixOS
        |
графика / звук / ввод / сеть / файлы
        |
      PhoenixOS
```

Для игр графическая часть дополняется:

```text
Direct3D 8/9/10/11 -> DXVK ---------+
                                     |
Direct3D 12 -> vkd3d-proton -> Vulkan -> графический драйвер PhoenixOS
```

Среда совместимости не является виртуальной машиной с Windows и не включает копию Windows.

## Путь 1. Нативная пересборка

### Шаг 1. Определить внешние зависимости

Нужно составить перечень:

- системных вызовов;
- библиотек;
- графического API;
- звукового API;
- сетевого API;
- работы с потоками и синхронизацией;
- файловых путей;
- средств сборки;
- сторонних двоичных компонентов.

Зависимости делятся на переносимые и привязанные к конкретной ОС.

### Шаг 2. Убрать прямую зависимость от ОС

Код приложения не должен размазывать вызовы конкретной ОС по всему проекту. Создаётся небольшой платформенный слой:

```text
логика приложения
      |
платформенный интерфейс
      |
+-----+---------+
|               |
PhoenixOS       другие ОС
```

Для существующего проекта такой слой часто уже есть.

### Шаг 3. Подключить библиотеки PhoenixOS

Целевой комплект разработки должен предоставлять:

- стандартную библиотеку C;
- слой POSIX;
- потоки и синхронизацию;
- файловый ввод-вывод;
- сокеты;
- время и таймеры;
- динамические библиотеки;
- графику;
- звук;
- клавиатуру, мышь и игровые контроллеры;
- шрифты;
- буфер обмена.

### Шаг 4. Собрать и проверить

Минимальные проверки переноса:

- запуск;
- создание и завершение потоков;
- чтение и запись файлов;
- сеть;
- ввод;
- звук;
- графика;
- полноэкранный режим;
- масштабирование;
- корректное завершение;
- отсутствие записи за пределами разрешённых каталогов.

### Шаг 5. Упаковать

Порт должен получать пакет PhoenixOS с:

- версией приложения;
- архитектурой;
- зависимостями;
- разрешениями;
- файловыми ассоциациями;
- значком;
- командой запуска;
- лицензией;
- сведениями об исходном проекте.

## Путь 2. Игры с открытым исходным кодом

Игры с исходным кодом являются хорошими первыми кандидатами для проверки мультимедийной платформы.

Приоритет имеют проекты, где платформа уже отделена от игровой логики и используется SDL либо похожий переносимый слой.

Для первого набора портов желательно выбрать разные классы:

- простая двухмерная игра;
- трёхмерная игра;
- игра с контроллером;
- сетевой многопользовательский проект;
- игра со звуком и потоковой загрузкой ресурсов.

Это позволит проверить не отдельную игру, а полноту платформы PhoenixOS.

## Путь 3. Windows-программы без исходного кода

### Общая схема

Среда совместимости реализуется в пользовательском пространстве. Она получает Windows-бинарник, загружает PE-модули и предоставляет ожидаемые программой Windows API через совместимый слой.

PhoenixOS не должна включать закрытые системные файлы Microsoft для того, чтобы этот путь работал.

### Базовый кандидат — Wine

Wine используется как исходная база реализации Windows API. Для PhoenixOS потребуется адаптировать его нижний платформенный слой к собственным:

- процессам;
- потокам;
- виртуальной памяти;
- файловой системе;
- сокетам;
- таймерам;
- синхронизации;
- окнам;
- вводу;
- звуку;
- динамической загрузке.

Цель состоит не в том, чтобы копировать внутреннее устройство Linux, а в том, чтобы предоставить Wine необходимые примитивы через POSIX-совместимый и специальный платформенный слой PhoenixOS.

### Игровая графика

Для современных Windows-игр основным направлением является Vulkan.

Планируемая цепочка:

- Direct3D 8, 9, 10 и 11 — через DXVK;
- Direct3D 12 — через vkd3d-proton;
- игры с Vulkan — через нативный загрузчик Vulkan PhoenixOS;
- OpenGL — через переносимый графический слой.

Это означает, что полноценная игровая совместимость напрямую зависит от качественного Vulkan-драйвера.

### Изолированное окружение программы

Каждая Windows-программа получает отдельное окружение:

- виртуальный диск C:;
- собственные настройки;
- собственный набор подключённых библиотек;
- отдельный кэш преобразованных шейдеров;
- отдельные разрешения PhoenixOS;
- отдельный журнал совместимости.

Пользователь может удалить такое окружение целиком, не затрагивая остальные программы.

## 64 и 32 бита

Первый этап — 64-разрядные приложения x86-64.

Старые игры часто остаются 32-разрядными, поэтому 32-разрядная совместимость является важной последующей задачей. Она потребует отдельной проверки загрузки PE32, библиотек, переключения соглашений вызовов и взаимодействия 32- и 64-разрядных компонентов.

Эта задача не должна усложнять первый рабочий 64-разрядный путь.

## Эталонные тяжёлые игры

Для проверки того, что среда совместимости пригодна не только для простых программ, PhoenixOS использует реальные тяжёлые игры как контрольные цели.

### The Witcher 3: Wild Hunt

The Witcher 3 используется как первая крупная контрольная игра. Целевой путь — запуск оригинального Windows-бинарника через среду Win64-совместимости.

Актуальная версия игры переходит на DirectX 12, поэтому основной графический путь для неё — Wine-совместимый слой -> vkd3d-proton -> Vulkan -> драйвер PhoenixOS. Более ранние версии с DirectX 11 также полезны для проверки DXVK.

Проверяются:

- запуск и прохождение заставки до игрового мира;
- сохранения и загрузки;
- клавиатура, мышь и контроллер;
- звук;
- полноэкранный и оконный режимы;
- компиляция и кэширование шейдеров;
- потоковая загрузка ресурсов;
- средняя частота кадров;
- нижний 1% частоты кадров;
- 95-й и 99-й процентили времени кадра;
- загрузка процессора и видеокарты;
- использование оперативной и видеопамяти;
- время загрузки сохранения;
- длительная сессия без утечки памяти.

### Cyberpunk 2077

Cyberpunk 2077 используется как следующая контрольная цель и стресс-проверка современного графического и системного стека. Игра требует DirectX 12, поэтому для неё ключевой путь — vkd3d-proton поверх Vulkan.

Дополнительно проверяются:

- большие объёмы отображений виртуальной памяти;
- интенсивная многопоточность;
- потоковая загрузка данных с SSD;
- высокий объём видеопамяти;
- современные возможности Vulkan, необходимые для эффективного D3D12;
- масштабирование изображения;
- трассировка лучей там, где её поддерживает выбранный драйвер;
- отсутствие длительных задержек при компиляции шейдеров;
- стабильность длительной игровой сессии.

### Критерий производительности

Сравнение проводится с Windows на одном физическом компьютере. Для каждого измерения фиксируются одинаковые:

- версия игры;
- сохранение или встроенный тест;
- разрешение;
- графический профиль;
- масштабирование;
- трассировка лучей;
- версия драйвера либо максимально близкий сопоставимый драйвер;
- частоты процессора и видеокарты;
- фоновые процессы.

Основная цель зрелого слоя совместимости — не более 5% потери средней частоты кадров относительно контрольного запуска Windows при сопоставимом времени кадра. Это цель, а не гарантированное свойство каждой игры.

Отдельно фиксируются случаи, где PhoenixOS быстрее Windows. Такое преимущество считается подтверждённым только после повторяемых измерений; оно не должно достигаться отключением корректности, безопасности, синхронизации или качества изображения.

До появления собственного стабильного Vulkan-драйвера эти игры являются целями архитектуры, а не обещанием текущей версии PhoenixOS.

## Steam и другие магазины

Поддержка конкретного магазина отделяется от поддержки самой игры.

Возможны три варианта:

- нативный клиент магазина, если поставщик его предоставляет или его можно законно перенести;
- запуск Windows-клиента через среду совместимости;
- установка игры независимым способом, если лицензия и магазин это разрешают.

Proton рассматривается как важный источник проверенных решений для игровой совместимости, но PhoenixOS не должна архитектурно зависеть от Steam.

## Античиты и защита от копирования

Особый класс проблем создают:

- античиты с Windows-драйверами ядра;
- защита от копирования с драйверами;
- программы, проверяющие точные внутренности Windows;
- аппаратные служебные программы, требующие фирменного Windows-драйвера.

PhoenixOS не будет загружать такой Windows-драйвер непосредственно в своё ядро.

Если античит или защита поддерживает пользовательский режим либо предоставляет официальный путь для совместимых систем, интеграция может быть добавлена. В противном случае конкретная игра отмечается как несовместимая.

Обход защиты от копирования не является задачей среды совместимости.

## Таблица совместимости

Для каждого проверенного приложения фиксируются:

- точное название и версия;
- архитектура;
- источник установки;
- версия среды совместимости;
- используемый графический путь;
- параметры запуска;
- статус запуска;
- работоспособность графики;
- работоспособность звука;
- работоспособность сети;
- ввод и контроллеры;
- сохранения;
- известные ошибки;
- наличие античита или защиты от копирования;
- результат повторной проверки после обновления PhoenixOS.

Статусы должны отражать фактическую воспроизводимую проверку, а не предположение.

## Автоматизация переноса

Комплект разработки PhoenixOS должен содержать помощник, который:

1. определяет систему сборки;
2. проверяет известные зависимости;
3. показывает отсутствующие интерфейсы;
4. создаёт заготовку платформенного слоя;
5. собирает пакет;
6. запускает проверки;
7. формирует отчёт о переносимости.

Для Windows-бинарников отдельный диагностический режим среды совместимости должен собирать отсутствующие DLL, функции Windows API, графические возможности и причины завершения.

## Критерий готовности направления

Направление переноса считается практически работающим, когда одновременно существуют:

- документированный нативный порт реальной сторонней программы;
- нативный порт реальной игры;
- воспроизводимый шаблон проекта;
- автоматическая сборка;
- пакет PhoenixOS;
- таблица совместимости;
- как минимум один проверенный Win64-бинарник в среде совместимости;
- как минимум одна проверенная Windows-игра с аппаратно ускоренной графикой.

Количество поддерживаемых игр затем расширяется постоянно, без изменения архитектуры ядра.
