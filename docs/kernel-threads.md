# Контексты потоков ядра

Работа над потоками ядра начинается с низкоуровневого переключения контекста x86-64. Этот слой не выбирает следующую задачу: выбор остаётся обязанностью планировщика.

## Сохраняемый контекст

При переключении сохраняются регистры, которые по соглашению вызовов должен сохранять вызываемый код:

- RBP;
- RBX;
- R12;
- R13;
- R14;
- R15;
- указатель стека RSP.

Адрес возврата уже находится на стеке и восстанавливается обычной инструкцией возврата.

Новый поток получает отдельный стек. Его вершина выравнивается по требованиям системного соглашения вызовов x86-64, после чего заранее формируется кадр первого восстановления. В R12 помещается адрес точки входа, а в R13 — один машинный аргумент. После первого восстановления небольшой переходник передаёт аргумент функции потока.

## Проверка в ядре

После запуска кучи, но до запуска периодического таймера, ядро выделяет отдельный стек размером 64 КиБ и создаёт тестовый контекст.

Проверка выполняет реальную последовательность:

1. основной контекст сохраняет собственный стек;
2. процессор переходит на стек тестового потока;
3. тестовый поток отмечает факт запуска;
4. тестовый поток сохраняет свой контекст и возвращает управление основному;
5. основной контекст проверяет отметку и продолжает загрузку.

Успешная проверка выводит строку:

`thread context self-test: OK`

Эта строка обязательна для QEMU-проверки ветки потоков.

## Объект потока и жизненный цикл

`KernelThread` владеет выделенным стеком, подготовленным контекстом и идентификатором. Состояния ограничены набором `Ready`, `Running`, `Blocked` и `Finished`; операции запуска, блокировки, пробуждения и завершения отклоняют недопустимые переходы.

QEMU-проверка создаёт объект потока, проверяет его свойства, выполняет реальное переключение на принадлежащий ему стек, возвращается и подтверждает завершённое состояние маркером `kernel thread object self-test: OK`.

## Связь с планировщиком и завершение

Следующий слой связывает объекты потоков с `phoenix-scheduler`. Менеджер потоков регистрирует каждый поток в круговом планировщике, синхронизирует блокировку и пробуждение с признаком готовности и выполняет выбранный контекст на отдельном стеке.

Для функций потока, которые могут завершиться, используется отдельный системный переходник. После возврата пользовательской функции он вызывает обработчик завершения, переводит поток в состояние `Finished` и переключается на выделенный контекст диспетчера. Только после возврата на стек диспетчера поток удаляется из очереди и освобождается принадлежащий ему стек.

QEMU-проверка создаёт два потока. Второй сначала блокируется, первый выбирается планировщиком и штатно завершается, затем второй пробуждается и проходит тот же путь. После удаления обоих потоков диспетчер обязан перейти в простой. Успешный путь подтверждается маркером `kernel thread scheduler self-test: OK`.

## Аппаратный сигнал вытеснения

Локальный APIC поддерживает один зарегистрированный обработчик системного тика. Обработчик вызывается после подтверждения прерывания через EOI, поэтому планировочный слой не удерживает активное прерывание APIC во время дальнейшей обработки.

Менеджер потоков получает номер реального аппаратного тика через этот интерфейс. Отдельный ассемблерный вход помещает RAX, RBX, RCX, RDX, RSI, RDI, RBP и R8–R15 прямо на текущий стек прерывания. За ними остаётся аппаратный кадр long mode с RIP, CS, RFLAGS, RSP и SS. Для `iretq` в 64-битном режиме эти пять слов нужны и при возврате на тот же CPL; это существенно для искусственно подготовленного кадра нового kernel stack.

Rust получает указатель на этот стековый кадр. Исходный RSP берётся из сохранённого процессором long-mode кадра. После обработки тот же ассемблерный вход восстанавливает регистры из кадра и выполняет `iretq`.

Глобальный буфер снимка регистров больше не используется. Rust-обработчик возвращает адрес кадра, который должен быть восстановлен, а ассемблерный выход после вызова Rust устанавливает `RSP` в возвращённый адрес. Если планировочный обработчик не выбирает другой кадр, автоматически используется адрес текущего прерывания.

Таким образом, путь возврата уже допускает замену всего прерываемого контекста одной сменой указателя стека. QEMU проходит несколько реальных таймерных IRQ через этот путь и подтверждает маркерами `thread preemption hook self-test: OK`, `thread interrupt frame self-test: OK`, `thread general register frame self-test: OK`, `thread stack interrupt frame self-test: OK` и `thread resumable interrupt frame self-test: OK`.

Добавлен `PreparedKernelTimerFrame`, чьё `repr(C)`-представление точно повторяет последовательность пятнадцати регистров, ожидаемую ассемблерным выходом, и аппаратные слова RIP/CS/RFLAGS для `iretq` без смены уровня привилегий. Загрузочная проверка подтверждает размер, смещения, нулевые начальные регистры, кольцо 0 и обязательные флаги маркером `thread prepared interrupt frame self-test: OK`.

## Следующий инкремент

Пункт «потоки ядра» остаётся открытым. Подготовленный кадр теперь размещается на отдельном стеке и начинает выполнение с замаскированными IRQ. Контрольная точка подтверждает вход, после чего явно разрешает прерывания для возвратного тика. QEMU через реальные тики APIC доказывает переход `iretq` на этот стек и последующее восстановление исходного кадра маркером `thread iretq stack switch self-test: OK`. Объект `KernelThread` хранит собственный сохранённый IRQ-frame; нулевые и невыровненные адреса отклоняются, а жизненный цикл значения проверяется маркером `kernel thread interrupt frame self-test: OK`. `ThreadManager` теперь сохраняет кадр текущей задачи перед очередным решением `RoundRobinScheduler` и возвращает ранее сохранённый кадр выбранной задачи. Загрузочная проверка проходит последовательность первый поток → второй поток → обновлённый кадр первого потока и требует маркер `kernel thread preemption scheduler self-test: OK`. Следующий шаг — подключить этот путь непосредственно к реальному APIC timer hook вместо специального двухфазного тестового селектора.
