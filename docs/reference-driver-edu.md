# Эталонный драйвер QEMU EDU

Этот пример показывает полный цикл разработки PCI-драйвера PhoenixOS: обнаружение, регистрацию, проверку совместимости интерфейсов, отображение регистров, обмен через DMA, аппаратное прерывание MSI, безопасную остановку и освобождение ресурсов.

## Где находится код

| Расположение | Назначение |
|---|---|
| `drivers/reference-edu/src/lib.rs` | Независимая `no_std`-часть: идентификаторы, регистрация, ограничение DMA, очередь причин прерываний, модульные проверки |
| `kernel/src/reference_edu.rs` | Проверочный адаптер ядра: MMIO, физический распределитель, `DmaBuffer`, аппаратный MSI, обмен с EDU |
| `kernel/src/arch/x86_64/exceptions.rs` | Вектор прерывания EDU `0xE1` в таблице обработчиков |
| `kernel/src/arch/x86_64/apic.rs` | Подтверждение прерывания через x2APIC |
| `scripts/qemu-hotplug.py` | Запуск QEMU с `-device edu,id=phoenix-edu` |
| `tests/qemu/bootstrap.markers` | Обязательные признаки успешной работы драйвера |

Никакая настоящая карта с похожим идентификатором не объявлена поддерживаемой: **разрешён только виртуальный контроллер QEMU EDU `1234:11e8`**.

## Обнаружение и регистрация

Контроллер находится посредством существующего перечисления PCI через ECAM. Отдельного списка шин или второго реестра драйверов не создаётся.

```rust
let mut context = ProbeContext::default();
let launched = phoenix_reference_edu::start_reference(pci_function, &mut context)?;
```

Функция создаёт `DriverRegistry<1, ContextRegisteredDriver<ProbeContext>>`, регистрирует `DriverDescriptor` с точными `vendor_id=0x1234`, `device_id=0x11e8` и запускает выбранный обработчик. Проверка отклоняет другой PCI-контроллер, несовместимую версию интерфейса `DRIVER_ABI_VERSION` и повторную регистрацию одинаковой версии.

Версия самого примера `0.3.0` отделена от версии интерфейса реестра: обновление драйвера само по себе не разрешает работу с несовместимым ABI.

## Регистры

Через существующую таблицу страниц ядра отображается только первая страница физического BAR0. Используются запись и чтение с аппаратным подтверждением. Отображение отмечено некэшируемым, запись в адреса AMD/NVIDIA/NVMe запрещена.

Перед обменом проверяются идентификатор EDU и работа регистра проверки связи. Состояние PCI Command сохраняется и восстанавливается после остановки драйвера.

## DMA: настоящий обмен, а не имитация

1. Системный распределитель выдаёт одну физическую страницу в диапазоне, доступном DMA EDU: **ниже 256 МиБ** (28-битная маска).
2. Общий `DmaBuffer` получает область через `DmaBufferPlatform`, а `QemuDirectDma` предоставляет допустимый адрес устройства. Смешивать виртуальный адрес процессора и адрес устройства нельзя.
3. В страницу записывается проверочный образец **256 байт**.
4. Контроллер получает аппаратные команды переноса памяти гостя → внутренняя память EDU по адресу `0x40000`.
5. Содержимое исходной страницы обнуляется, после чего устройство переносит данные обратно в гостевую память и генерирует MSI.
6. Ядро сверяет все 256 байт, подтверждает завершение DMA, закрывает отображение устройства, затем возвращает физическую страницу.
7. Счётчик свободных страниц должен восстановиться точно до исходного значения: **1/1 возвращена**.

Запрещено освобождать активную DMA-область. При неподтверждённом завершении устройство не должно терять право владения буфером — иначе возможен доступ к уже освобождённой памяти. Отказ закрытия сохраняет состояние для диагностики.

На QEMU без IOMMU используется проверенная прямая адресация; переносимость на физическую машину и работа с IOMMU пока не доказаны.

## Прерывания: настоящий MSI

В таблицу прерываний установлен отдельный вектор `0xE1`. EDU получает адрес доставки MSI в локальный APIC процессора и передаёт два события:

- `0x42` — вызов проверочного прерывания через регистр EDU;
- `0x100` — аппаратное прерывание по завершении второго DMA.

Обработчик не выделяет память и не пишет в журнал. Он читает регистр причины `0x24`, подтверждает её регистром `0x64`, публикует результат через атомарный `InterruptMailbox` и отправляет подтверждение завершения прерывания в x2APIC. Длительное ожидание и анализ происходят уже в обычном контексте ядра.

Перед освобождением отображения устройства настройка MSI отключается, адрес обработчика отзывается, а исходные регистры PCI восстанавливаются. Пример ориентирован на один виртуальный процессор QEMU и не является готовым общим распределителем MSI/MSI-X по ядрам.

## Проверки

**Модульные** — правильный выбор PCI, отклонение NVIDIA и иных устройств, отказ несовместимого ABI и дублирования версии, границы 28-битного DMA, доставка и очистка причин прерываний, запрет возврата активной памяти и закрытие отображений.

**Аппаратные в QEMU** — ядро обнаруживает виртуальный EDU, подтверждает идентификатор и MMIO, получает реальное MSI `0x42`, выполняет два DMA-переноса, получает MSI `0x100`, сверяет 256 байт и возвращает страницу.

Обязательные строки журнала:

```text
reference edu driver: OK bus=0 device=4 bytes=256 driver=qemu-edu-reference
reference edu irq dma: OK mask=0x142 returned_pages=1
```

Также должны успешно пройти прежние проверки NVMe/PhoenixFS, xHCI/USB, виртуальной графики и пользовательских программ.

Для проверки используется стандартная команда автоматического испытания из `scripts/run-qemu-ci.sh` (сборка образа выполняется по существующему процессу). Драйвер присутствует в составе рабочего пространства Rust и автоматически собирается вместе с ядром.

## Обработка отказов после аудита

При каждом начале аппаратного испытания очищается накопленный набор причин IRQ, чтобы повторная попытка не могла ошибочно принять старое прерывание за новое. В случае отказа подтверждения MSI прежняя конфигурация восстанавливается; после проверки регистров, включения MSI или выполнения DMA на любом выходе отключается обработка MSI и снимается адрес глобального обработчика. При ошибке PCI Bus Master запрещается, MMIO-отображение снимается.

Если **обе** аппаратные передачи подтвердили завершение, буфер DMA освобождается даже тогда, когда отдельная проверка содержимого или доставки IRQ не прошла. Если реальное завершение передачи не подтверждено, страницу не возвращают в общий распределитель: безопаснее сохранить за устройством закреплённую память до остановки и перезагрузки учебной виртуальной машины. Это не универсальная система восстановления неисправного контроллера.

Разбор ограничений и результатов проверки — [акт аудита 0.3](audit-0.3.md).

## Как использовать образец для нового драйвера

1. Создать независимую библиотеку `no_std` в каталоге `drivers/`.
2. Задать собственный точный профиль устройства и декларацию `DriverDescriptor`.
3. Проверить совместимость `DRIVER_ABI_VERSION` через штатный реестр.
4. Передавать ресурсы запуска через контекст; не хранить непроверенные адреса в глобальных указателях.
5. Отображать BAR только с проверкой размера и атрибутами кэширования; соблюдать размеры аппаратных регистров.
6. Использовать общий `DmaBuffer` и платформу отображения устройства; никогда не приравнивать адрес процессора к адресу DMA без доказанного режима.
7. Разделять короткий обработчик IRQ и работу с данными после IRQ; подтверждать причину на устройстве и сигнализировать EOI.
8. Перед возвратом памяти подтверждать завершение DMA, маскировать прерывания, прекращать доступ устройства к области и снимать отображения.
9. Добавить испытания ошибочных границ, версий, таймаутов, повторного закрытия и реальной работы в QEMU.

## Ограничения

Это минимальный **функционирующий эталон**, а не универсальная библиотека загрузки сторонних драйверов. Пока нет общего распределителя векторов MSI/MSI-X, многопроцессорного назначения MSI, управления питанием, аппаратного IOMMU и испытаний физических карт. Некоторые другие драйверы PhoenixOS ещё используют собственные адаптеры ядра; их миграция на общие интерфейсы относится к следующим этапам.
