# Диагностический образ PhoenixOS для ASUS

Дата подготовки: 9 ноября 2026 года. Назначение — предварительное исследование целевого ноутбука ASUS VivoBook Pro 15 M6500QH перед аппаратными испытаниями DMA.

## Зачем требуется отдельный образ

**Штатный проверочный образ PhoenixOS нельзя запускать на реальном ноутбуке.** Виртуальный сценарий управляет NVMe и проверяет запись в тестовые блоки. Он разработан для QEMU и может повредить данные при использовании на физическом накопителе.

Диагностический образ собирается из независимого `diagnostic-kernel`. Он не включает обычное ядро, драйверы NVMe/xHCI, PhoenixFS, управление DMA-буферами и запуск устройств. В нём нет интерфейса сохранения отчёта на накопитель.

## Что диагностируется

- Поставщик и модель процессора по CPUID, длина физического адреса, признаки поддержки PAT/MTRR.
- Текущие регистры PAT, MTRR и число поддерживаемых переменных диапазонов, фиксированные MTRR первого мегабайта; **только чтение**.
- Проверка ограниченной программной политики WriteBack, без перепрограммирования кэширования или создания второго отображения RAM.
- Таблицы ACPI, наличие MCFG и подписей IVRS (AMD) или DMAR (Intel). Наличие IVRS/DMAR **не подтверждает включённый IOMMU**.
- Чтение идентификаторов и классов PCIe через MCFG/ECAM. Драйверы хранения, графики, USB и сети не запускаются.
- Отчёт выводится на экран средствами переданного загрузчиком UEFI GOP и в последовательный порт COM1, если он существует.

Если таблицы ACPI, конфигурация CPU или адреса ECAM неподдерживаемы, диагностика сообщает об ограничении и **не переходит к управлению контроллерами**. Операции в режиме ошибки не должны предполагать, что аппаратная проверка пройдена.

## Сборка

Нужны инструментарий Rust из `rust-toolchain.toml` и компоненты для `x86_64-unknown-none`. В корне репозитория:

```sh
cargo run -p phoenixos-diagnostic-image --release --quiet
```

Команда выводит абсолютный путь к `phoenixos-diagnostic-uefi.img`. Для штатного образа используется **другая команда** — `cargo run --release --quiet`; путать их нельзя.

В автоматической проверке GitHub после сборки и запуска QEMU появляется отдельный артефакт **`phoenixos-diagnostic-uefi`**, содержащий `phoenixos-diagnostic-uefi.img`. Тестовый сценарий:

```sh
python3 tests/platform/test-diagnostic-isolation.py
python3 scripts/run-diagnostic-qemu.py artifacts/phoenixos-diagnostic-uefi.img artifacts/diagnostic-serial.log
```

Для запуска второго сценария нужны QEMU, OVMF и KVM. Виртуальная машина получает единственный загрузочный образ в режиме чтения и собственную временную копию переменных OVMF. Физический накопитель компьютера-исполнителя к QEMU не подключается.

## Перед первым запуском на ASUS

**Испытания на физическом ASUS ещё не проводились.** После проверки готового образа в QEMU нужно отдельно подтвердить возможность восстановления обычной загрузки Windows. Подготовить резервную копию важных данных, убедиться в наличии доступа к ключу восстановления BitLocker, если шифрование включено, и проверить способ возврата к штатной загрузке. На текущем этапе нельзя утверждать абсолютную безопасность запуска непроверенного ядра на настоящей прошивке.

Для проверки требуется **отдельная пустая флешка**, поскольку запись загрузочного образа удаляет содержимое выбранного USB-носителя. При записи необходимо определить накопитель по размеру и модели и **не выбрать внутренний SSD**. Никаких изменений разметки внутреннего накопителя или параметров BIOS/UEFI ради проведения эксперимента не делать.

Только после готовности плана восстановления можно выбрать однократную загрузку внешнего носителя через меню UEFI. Если образ не загружается или экран не показывает явный заголовок **`PhoenixOS`** и строку **`diagnostic mode: OK readonly=1`**, эксперимент прекратить, не повторять с обычным UEFI-образом PhoenixOS.

**Ограничение:** даже наше диагностическое ядро не выдаёт команд записи на внутренний SSD, однако UEFI-прошивка, загрузчик или аппаратное обеспечение могут изменять собственное служебное состояние. Нулевой риск загрузки чужого образа на физическом ПК гарантировать нельзя.

## Получение результата

Первый вариант отчёта предназначен для **фотографии экрана**. Там отображаются основные сведения; подробные записи PCIe и регистров выводятся в COM1, если интерфейс доступен. На большинстве ноутбуков COM1 физически отсутствует; **сохранение всего отчёта в файл пока не реализовано**. Поэтому при отсутствии COM1 часть подробностей будет недоступна для передачи, и критерий полноценной аппаратной приёмки не будет закрыт. Для удобного сбора полного отчёта потребуется отдельный безопасный механизм экспорта, а не включение файловых драйверов основного ядра.

Приемка аппаратного пункта **16/17** потребует отдельного подтверждения реальных PAT/MTRR, прямых отображений RAM, расположения физических областей и отсутствия конфликтов. Пункт **17/17** дополнительно требует реально выполненный DMA-обмен на разрешённом физическом контроллере с безопасной остановкой и освобождением памяти. Одно успешное появление отчёта **не закрывает** ни один из этих критериев. Полноценный IOMMU — отдельная работа.

## Граница безопасности и планы

Образ не предназначен для установки, тестирования скорости накопителей, прошивки, включения AMD-Vi или проверки DMA-обмена. Для настоящего испытания устройства необходим отдельный явно разрешённый профиль с контролем записи и аппаратной остановки. До этого состояние расширенного DMA остаётся **15/17**.
